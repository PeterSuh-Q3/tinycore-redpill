# DSM resolver 커널 5 플랫폼 관리 설계

## 목표와 지원 범위

기존 resolver의 검토된 설정에서 커널 5 플랫폼 정책을 함께 관리한다. 초기 지원 플랫폼은 `epyc7002`, `epyc7003`, `icelaked`, `v1000nk`, `r1000nk`, `geminilakenk` 여섯 개다. `epyc7003ntb`는 모든 신규 및 기존 빌드 진입점에서 지원하지 않는다. 기존 커널 3/4 플랫폼 지원은 유지한다. 이 문서는 설계이며 구현이나 배포 결과를 의미하지 않는다.

## 현황과 문제

- `functions.sh`, `functions_t.sh`, `redpill-load/ext-manager.sh` 및 테스트 트랙에는 NTB를 포함한 7개가 하드 코딩되어 있다. Friend `boot.sh`에는 4개만 있어 `epyc7003`, `icelaked`가 누락되어 있다.
- 현재 컴파일된 resolver 카탈로그의 커널 5 대상은 위 6개이며 NTB 대상은 없다. 그러나 redpill-load 설정과 모듈·애드온 인덱스에는 NTB 항목이 남아 있다.
- 같은 목록을 커널 선택, 확장 키, DT 및 네트워크 처리에 재사용한다. 각 조건의 의미가 같다고 단정하면 신규 플랫폼에서 잘못된 분기가 발생할 수 있다. 예를 들어 LKM 파일명만으로 실제 대상 커널을 판별하지 않는다.
- Friend는 일치하는 resolver 메타데이터의 커널을 우선 사용하지만, 메타데이터가 없거나 불일치하면 별도 목록으로 대체한다.

## 데이터와 resolver 계약

검토 원본인 `redpill-load/config/catalog/dsm-targets.v1.json`에 선택적 `platform_policy` 객체를 추가하고 기존 `tools/compile-dsm-targets.py`가 검증하여 `tinycore-redpill/config/dsm-targets.v1.json`에 포함한다. 기존 스키마 1 읽기 계약을 유지하는 추가 필드이며, 새 소비자는 필드가 없으면 정책 사용 불가로 처리한다. 예시:

```json
{
  "platform_policy": {
    "version": 1,
    "kernel5_platforms": ["epyc7002", "epyc7003", "icelaked", "v1000nk", "r1000nk", "geminilakenk"],
    "excluded_platforms": ["epyc7003ntb"],
    "traits": {
      "epyc7002": {"dt": true, "extension_key": "platform_release_kernel"}
    }
  }
}
```

예시는 구조만 나타낸다. 실제 traits는 여섯 플랫폼 각각에 대해 현재 분기와 실제 대상 설정을 조사해 채운다. `kernel5_platforms`는 지원 가능한 플랫폼 집합이고 실제 선택한 DSM의 정확한 커널은 반드시 해당 `targets[]` 레코드의 `kernel`을 사용한다. 플랫폼 하나에 다른 세대 커널이 존재할 수 있으므로 플랫폼 이름만으로 정확한 커널을 고정하지 않는다. DT, 확장 키 형식 및 개별 패치 조건은 독립된 명시적 속성이나 대상별 조건으로 정의하며, 현재 동작과의 차이를 확인한 뒤 전환한다.

컴파일러는 중복, 알 수 없는 속성, 허용·제외 교집합, NTB 대상 또는 NTB 활성 레시피, 정책과 대상 커널의 불일치를 오류로 처리한다. 초기 데이터는 정확히 여섯 개이며, 이후 추가는 검토된 정책과 실제 대상·레시피를 함께 추가할 때만 가능하다. 정책을 카탈로그 식별자 계산에 포함하고 동일 입력에 동일 결과를 생성한다. 기존 카탈로그 구조와 해시 계산 방식에 맞춰 구현한다.

resolver에 `platform-policy` 조회를 추가하여 플랫폼별 지원 상태와 traits를 반환한다. 기존 대상 조회도 제외 플랫폼을 명시적으로 거부하고 `PLATFORM_EXCLUDED`를 반환한다. 알 수 없는 플랫폼, 누락·손상된 정책, 대상과 커널 불일치는 각각 오류로 처리하며 커널 4로 자동 대체하지 않는다. 플랫폼의 별칭과 `(DT)` 표시를 입력 경계에서 정규화하고 원본 플랫폼 이름으로 정확히 비교한다.

## 저장소별 적용

| 저장소 | 변경 설계 |
| --- | --- |
| tinycore-redpill | resolver와 브리지에 정책 조회 추가. `functions.sh`와 `functions_t.sh`를 함께 변경하고, `menu_m.sh`의 DT 및 R8168 분기는 각각의 속성으로 전환한다. 테스트 시뮬레이터의 별도 목록도 제거한다. 빌드 중 선택 결과를 고정해 반복 조회와 중간 갱신에 따른 불일치를 방지한다. |
| redpill-load | 두 `ext-manager`의 키 선택을 정책으로 전환하고 직접 실행 진입점에서도 NTB를 거부한다. NTB 설정은 활성 경로에서 제거한다. 기존 resolver 대상별 config와 모듈 recipe 검증은 유지한다. |
| tcrpfriend | 일치하는 resolver 메타데이터의 정확한 커널을 우선 사용한다. 구형 설정에 필요한 6개 플랫폼 대체 정책을 공통 원본에서 생성해 이미지에 포함한다. NTB는 대체 분기 진입 전 거부한다. 정확한 커널을 안전하게 결정할 수 없으면 오류를 표시하고 중단한다. |
| tcrp-modules / tcrp-addons | 활성 인덱스에서 NTB 키를 제거하고 NTB 전용 `ntbfsdn`을 활성 배포 대상에서 제외한다. 생성 또는 검증 단계에서 공통 정책과 인덱스를 대조한다. 각 패키지는 실제 제공하는 플랫폼의 부분집합일 수 있으며, 여섯 플랫폼 전체에 패키지가 있다고 가정하지 않는다. |

기존 공개 릴리스 파일은 과거 산출물로 남길 수 있지만 활성 인덱스, 메뉴 및 빌드 경로에서 접근 가능한 지원 대상으로 취급하지 않는다. 직접 URL 사용을 포함해 모든 과거 배포본의 실행을 회수할 수는 없다.

## 전달과 호환성

공통 정책은 오프라인에서 사용할 수 있어야 한다. 컴파일 단계에서 카탈로그와 같은 원본으로 작은 정책 산출물을 생성하고, 이를 redpill-load와 Friend 이미지에 각각 포함한다. 산출물에는 정책 버전과 원본 식별자를 기록한다. 각 저장소 CI는 생성 결과와 원본 식별자를 대조해 불일치를 실패 처리한다. `my.sh.gz`에는 resolver 카탈로그와 필요한 조회 스크립트를 함께 포함하고, 설치 시 디렉터리 생성 및 카탈로그·스크립트의 일관된 교체를 검증한다. Friend와 redpill-load 단독 실행도 네트워크 조회에 의존하지 않는다.

정책을 읽지 못하거나 구버전 구성요소가 섞인 경우 조용히 기존 하드 코딩으로 돌아가지 않고 해당 신규 정책 경로를 중단하며 필요한 구성요소 업데이트를 안내한다. 이전 Friend 이미지 자체는 변경되지 않으므로, 새로운 동작을 보장하려면 정책을 포함한 Friend 업데이트가 필요하다. 배포 순서는 정책을 읽을 수 있는 redpill-load와 Friend, 그 다음 카탈로그와 MSHELL 소비자이며, 전환 기간의 버전 호환성은 배포 전 조합 시험으로 확인한다.

## 검증과 운영 절차

1. 여섯 플랫폼의 실제 지원 대상별 DSM·커널·모드에 대해 resolver, 메뉴 및 확장 키를 기존 정상 동작과 비교한다. `purley` 등 커널 5가 아닌 대상이 LKM 파일명 때문에 분류되지 않는지도 확인한다.
2. NTB를 resolver, 메뉴, 이슈 워크플로, 직접 빌드, 확장 관리자 및 Friend 구형 설정 경로에 각각 입력해 명시적으로 거부되는지 확인한다. 활성 인덱스와 모델 선택에도 NTB가 없어야 한다.
3. 정책 누락·손상·불일치, 오래된 Friend, 구형 설정, 오프라인 부팅을 시험한다. 여섯 플랫폼의 정확한 커널을 대상으로 확인하고, 근거 없는 대체 값을 허용하지 않는다.
4. 모듈·애드온 인덱스와 생성 산출물의 일치 여부, functions 두 파일의 동등성, `my.sh.gz`의 파일 및 경로를 검사한다. SA6400 7.4.1의 메뉴 및 이슈 빌드와 Friend 부팅을 회귀 시험한다.
5. 새 플랫폼은 원본 정책에 속성과 지원 대상으로 등록하고 DSM 대상, PAT, config, 호환 모듈 및 애드온을 검토한 뒤 컴파일·각 저장소 산출물 동기화·CI·실기 검증을 수행한다. 커널 5라는 이유만으로 자동 승인하지 않는다. 운영 가이드에 이 절차와 배포 순서를 추가한다.

## 구현 완료 기준

활성 코드의 중복 플랫폼 목록이 제거되고 6개 정책이 모든 소비자에 전달되어야 한다. NTB의 모든 활성 진입점이 차단되어야 하며, 다른 커널 계열과 기존 지원 대상의 회귀 시험이 통과해야 한다. 대상별 기능 특성과 Friend의 구형 설정 대체 커널은 실제 증거를 확인해 채우는 구현 작업이 남는다.
